You are building the complete frontend-first prototype of “Wellfarm,” based on the Product Requirements Document provided above.

Treat the PRD as the product source of truth. Build the actual runnable prototype, not a design document, wireframe, or static landing page. Continue until the application builds successfully and every major visible interaction works.

PRIMARY OBJECTIVE

Create a polished, competition-ready prototype that lets Smart India Hackathon judges understand the complete Wellfarm system through visible, interactive journeys:

1. Farmer crop scanning and localized advisory
2. India-wide regional outbreak monitoring
3. Weather–outbreak intelligence
4. Official recommendations
5. Laboratory routing
6. Laboratory/field verification
7. Monthly reports
8. Collective learning, retraining and caching

The application may use deterministic simulated data for features that are out of scope for Round 1, but those features must still be visible, interactive, coherent and clearly labeled.

This is a frontend-first prototype. Use a clean service-adapter architecture so mock services can later be replaced with real APIs without rebuilding the interface.

REPLIT INTEGRATIONS AND PLUGINS

Inspect the Replit integrations/plugins available in this workspace before implementation.

Use appropriate official Replit integrations where they materially help:

- Replit Secrets for API credentials
- Replit Database/Postgres for demo records if readily available
- Replit Object Storage for uploaded images if readily available
- Replit Auth only if it can provide a smooth role-based demo
- Replit AI/OpenAI integration for advisory generation if available

Do not add an integration only to claim it is being used. Do not block completion if an integration is unavailable. Implement an adapter and deterministic fallback instead.

Never expose secret keys in frontend code, logs or committed files. Any LLM request must run through a server-side endpoint.

REAL INTEGRATIONS WITH FALLBACKS

Weather:
- Use Open-Meteo with GPS coordinates when network access is available.
- If it fails, use a deterministic fallback and label it “Demo weather.”
- Cache the response briefly to avoid unnecessary repeated calls.

LLM:
- If a server-side OpenAI/Replit AI integration is configured, generate a structured advisory.
- Validate the structured response.
- Never expose the API key to the browser.
- If unavailable, use deterministic, prewritten advisories.
- Never invent pesticide dosage, waiting periods or regulatory claims.

Map:
- Use MapLibre.
- Use a properly licensed India state/district GeoJSON source.
- Preserve attribution.
- Do not fabricate official boundaries.
- If district geometry is unavailable, use a clearly labeled schematic fallback while keeping the map adapter replaceable.

GPS:
- Use browser geolocation.
- Handle permission denied, timeout and low-accuracy states.
- Provide a demo-location button.
